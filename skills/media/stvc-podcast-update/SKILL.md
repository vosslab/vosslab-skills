# Update a StVC podcast episode

## When to Use

Trigger: "update episode N," update a podcast page, or refine its thumbnail. Use the requested scope and the existing tools in `$HOME/nsh/stvc-podcast-tools/`.

## Respond to feedback

Use `~/nsh/stvc-podcast-tools/docs/TROUBLESHOOTING.md` when the user rejects facial realism/likeness/integration, requests explicit X/Y/Z content, or reports a failed stage. It maps feedback to inspection, concrete recovery, positive prompt examples, and verification. For X/Y/Z, record each requested element and relationship, give it a visible role, and verify it in the actual output. Describe the desired image positively; review the full result and then resume the matching recipe. The wiki entry is `~/wiki/podcast/guides/stvc-request-recipes.md`.

For persistent painted-face style lock, use the portrait-board-only recovery in `docs/TROUBLESHOOTING.md` under "Recover painted-face style lock". Inspect the liked composition, describe its positions/actions/wardrobe/project shapes/lettering in text, and generate from original portraits as the sole image input. This removes the stylized image's influence while preserving the concept. Verify likeness, scene preservation and head/body integration separately; this is a regenerated interpretation, not pixel-preserving editing.

### Discuss or revise culturally informed wardrobe

1. Distinguish a historical/style question from an instruction to revise artwork. Answer curiosity and offer a concrete styling direction without generating or replacing an accepted thumbnail; speculative preferences attributed to a host do not establish that host's approval.
2. Inspect the accepted image before proposing wardrobe changes. Identify the visible garments and coverage, then describe a scoped change that preserves the liked composition, recognizable face, and existing coverage. Do not invent details hidden by the crop.
3. For historical questions, retrieve dated evidence and distinguish presence in America from presence in the Western frontier, and classic Old West dates from later homesteading. Separate evidence about religious practice from evidence about clothing; a pioneer's biography does not establish what she wore. State when a proposed outfit is a modern thematic interpretation rather than a documented reconstruction.
4. Translate the theme into specific garments without treating religion as a uniform. For a modest Western look, consider a felt cowboy hat over the existing headscarf, loose long sleeves, and a longer Western vest or duster; preserve hair and neck coverage shown in the reference unless a change is requested. Treat these as design options, not a declaration of religious compliance or the host's personal standards. If an edit is requested, verify the actual clothing coverage, unobstructed likeness, and accessory fit in the generated image before publication.
5. Once the user requests the discussed revision, use the accepted artwork as composition authority and the inspected labeled original-photo board as identity authority. Map each person's requested role to concrete wardrobe, expression and props while preserving the successful scene, headline and anatomy. Translate film-character inspiration into the host's own eccentric styling rather than substituting an actor's face; a heroic cowboy role does not require adding weapons or replacing the scientific activity with an action scene. Inspect the native candidate, then export and review the full-size and mobile versions before a thumbnail-only publication. Preserve the previous accepted image in production, verify the replacement on the public CDN, and update only the selected wiki artwork and relevant episode knowledge.

## Robust completion

When image generation is absent from the current tool catalog, distinguish tool exposure from provider readiness. An existing Image Studio runner's `--check` proves registration/model only, not authentication. Check `hermes portal info` and `hermes portal tools` before paid invocation; a configured Nous model can coexist with a logged-out Portal. Retain prepared art and complete independent metadata when login is genuinely unavailable. Keep the configured billing route and credentials unchanged; provider restoration is a separate authorization decision.

Use the runbook's robustness policy as the canonical decision contract. Preserve useful operation when inputs or state are imperfect: classify the impact, choose the best safe recovery, record the assumption, and continue the next implied step. Each gate earns its place by identifying a real correctness problem and specifying a concrete recovery or terminal decision.

Routine milestones belong to the manager and reviewing agents, supported by existing validators and live readback. Carry an authorized update through publication without renewed human editorial approvals. Establish real scope and spending authorization at entry. The user explicitly authorizes rehosting existing already-public host portraits in public, unlisted storage for current and future podcast references; reuse that permission and the local reference registry. Newly private photos or unrelated personal material remain separate transfer decisions. Keep actual denials and privacy boundaries intact, and continue independent authorized work when one action is blocked.

Reuse explicit user-confirmed cast and corrected manifests. Treat uncertain optional names, mascot details, and guest biographies as omissions, not reasons to invent another participant or stop publication. Recover likeness references from existing approved portraits or adequate public episode artwork; document a weaker reference basis. Ask only when a required fact remains unrecoverable and materially affects the requested result.

The target is recognizable, lifelike hosts convincingly integrated into the scene. Evaluate likeness and integration separately and require both; a request for faithful likeness does not by itself request unchanged source pixels. Use `/srv/samba/share/wiki/podcast/great-faces.jpg` as the user's preferred face/integration example, `decent-faces.jpg` as the intermediate example, and `bad-photoshop-faces.jpg` as the rejected pasted-face treatment. These examples establish rendering quality, not episode layout or cast. Improve head/body integration with matched light direction, color temperature, perspective, neck contact shadows, and edge softness. An accepted result stays published unless another revision is requested. When realism is requested, prompt positively for lifelike adult anatomy, continuous skin tones, natural texture, believable materials, and motivated lighting. Compare the actual image beside the labeled photographic reference board and preferred rendering example, separately from technical validation and upload acceptance. Check that defining identity cues are used correctly, not merely present somewhere: eyeglasses held as a prop do not replace glasses normally worn on the face. Recover that scoped cue while preserving successful integration and the other hosts. Use an independent reviewer when available or an equivalent evidence-based assessment; reviewer availability alone is not a blocker. Evaluate the requested face realism within the intended imaginative game world; a literal photographic setting or forensic identity proof is a different requirement. Keep review findings actionable: significant likeness drift, insufficient face realism, broken anatomy, incorrect headline, or important content covered by the duration badge. Judge mobile legibility against the promotional purpose: the headline, faces and requested role cues must read, but small scientific marks need not be individually countable unless the thumbnail is explicitly a counting puzzle. A reviewer's off-scope objection is not a new acceptance criterion; record why it does not require a revision. Decorative scenery in the badge corner alone is not a blocker.

When a host rejects a likeness, do not infer or prompt an ethnicity from appearance or a name. Use the wiki's original photograph and describe only observable features. A reference-guided generator still redraws faces: never call its output an unchanged original-photo composite. If it keeps altering facial proportions, change the reference or composition strategy while retaining the likeness requirement. Deterministic original-photo compositing is a separate technique, not automatic recovery or proof of visual success. Use it when unchanged source pixels are explicitly requested or the composite actually meets both likeness and integration criteria; document source hash, placement, mask, and any color adjustment. Review duplicate features, seams, scale, lighting and public served pixels. Do not silently trade away integration to satisfy pixel provenance.

Treat `great-faces.jpg` as a final rendered example for output-quality comparison. Follow the wiki's actual source recipe: a labeled original-photo identity board plus an actual project/gameplay screenshot for a new scene; the candidate plus a needed correction board for an edit. Original portraits establish identity, episode evidence establishes the project, and the finished example helps assess rendering and integration. Review facial rendering, likeness, and integration separately; successful integration alone leaves a rejected rendering unresolved.

For more than three faces, use one labeled original-photo identity board within the route's actual image-input cap, and explicitly map each identity to its scene position and action. Distinguish unique people from intentional repeated appearances. Episode 35's demonstrated five-identity/seven-appearance recipe is in `~/wiki/podcast/guides/stvc-nano-banana-thumbnails.md`, "More than three faces: demonstrated Episode 35 recipe"; this is not a three-face provider limit or an unlimited-cast guarantee. After a targeted identity-cue repair, inspect related hands and props too: adding worn glasses can leave a second pair held in a hand. Describe the desired complete action positively (glasses worn, hands on steering control), then verify the actual output. Record a user-tolerated inconsistency without regenerating an accepted image unless requested.

For an all-cast likeness revision, inspect alternate wiki-listed originals before reusing the same board; a clearer frontal portrait can materially improve the input over a webcam crop. The user rejected `episode35/all-faces-original-board-v2.jpg` as insufficient for new Episode 36 work; rebuild an episode-specific board from inspected originals rather than treating that historical board as an approved default. Verify the actual identities in a saved board, not just its filename or prior manager's description. Give the rebuilt original-photo board primary identity authority and the existing artwork composition authority. If the requested Nano Banana pass still changes rejected facial geometry, preserve the candidate and diagnose the reference/scene conflict rather than automatically pasting original-photo masks. Consider a fresh coherent scene from the original portraits instead of repeatedly locking an unsuccessful scene; retain episode requirements and spending limits. Review final integration beside both the source board and the preferred rendering example; intentional repeated stunt appearances are not accidental duplicate-face defects. Distinguish a generated pass followed by original-pixel compositing from a claim that generation preserved original pixels. Reaching an actual resource limit establishes an unresolved attempt, not that better output is impossible.

For a host-specific likeness repair, lock the already-approved people, scene, props, and lettering in the prompt, and name the sole person whose face may change. Use the original portrait of that host as the identity authority; preserve its face orientation, proportions, hair, glasses, age cues, and natural asymmetry rather than accepting a generic attractive approximation. If the generation route has limited reference-image slots or an individual reference cannot be delivered promptly, use an existing approved labeled composite board containing that host; do not delay a scoped repair on redundant rehosting. Independently inspect the generated export and the public CDN image. Model visual assessment is evidence, not final authority over personal likeness: if the depicted host rejects the likeness, treat that as an unresolved quality failure, perform the next authorized targeted revision, and do not report the thumbnail as complete merely because it passed technical or agent review.

Start with one candidate and revise observed consequential defects within the existing spending/time authorization. When successive edits retain a painted or generic facial treatment, stop reference-editing that candidate: build or verify a labeled board from the original portraits, generate a fresh coherent scene from that board, and specify the retained composition, cast positions, actions, world elements, and lettering in the brief. Use the failed candidate only as a composition reference when its identity rendering is not being inherited by the route; otherwise it can perpetuate the defect. Inspect the new native output before exporting or publishing. Continue a concrete authorized recovery while it makes useful progress; use actual resource/authority limits and evidence of stalled progress to decide when to stop, rather than treating a fixed attempt count as proof of impossibility. Preserve completed metadata while image work continues. Keep the current live image until a suitable replacement is ready and report any unresolved required visual outcome accurately.

Review existing images directly with the image tool or give their existing paths to a reviewing agent. Comparison-sheet generation is optional presentation work, never a publication dependency; keep ad hoc inline-interpreter image manipulation out of the normal path.

An actual denied/timed-out action stays paused until renewed authorization; preserve its exact scope and respect the tool's stop instructions. Record what did and did not run. Once authorized to resume, continue from retained artifacts rather than redoing generation or reopening confirmed cast. Optional artifact failure does not establish a defect in the final image. Preserve global safety settings; broad allowlists or disabling approvals are not pipeline repairs.

`apply` and `verify` can exit 2 when a thumbnail was accepted and still needs visual readback. Read the JSON result and receipt. Run subsequent read-only fetch/CDN inspection as separate commands instead of chaining them with `&&` after that expected status. Never turn this exit code into a duplicate upload. If a normal apply returns metadata mismatch with thumbnail pending, first run read-only verification. Once metadata matches, establish from the normal return path and operation evidence that thumbnail dispatch never occurred; then reapply the same reviewed plan so metadata is a noop and only the outstanding image is uploaded. A generic tool-loop warning based on exit 2 does not override the structured receipt; inspect actual state rather than treating accepted-but-unverified as failed. Completion uses fresh intended-field comparison and preservation checks, plus public image inspection for artwork scope and description/link/chapter checks for the corresponding page scope.

## Execute

For the user's preapproved start-to-finish requirement, first read `~/nsh/stvc-podcast-tools/docs/UNATTENDED_PIPELINE.md`. Run `source source_me.sh` once separately, then one `python3 /home/vosslab/nsh/stvc-podcast-tools/stvc.py ...` command per terminal call. Workers use these same commands and file tools, not inline Python or shell snippets. The scoped allowlist covers named application entry points; global smart approvals remain enabled. A routine approval prompt is a pipeline defect to repair, not a recurring human milestone. Actual denials remain pauses until renewed authority. Native image/browser/vision tools own generation and review. Read the complete timestamped transcript output before writing copy.

1. Confirm the exact episode/video/channel and requested scope. For lightweight latest-episode discovery, fetch the official playlist Atom feed at `https://www.youtube.com/feeds/videos.xml?playlist_id=PLAYLIST_ID`; use its entry ID, title, publication time, and thumbnail URL as discovery evidence. Do not treat feed order as publication eligibility: reconcile the candidate against the channel state and its scheduled/live status before choosing an episode. Resume its checklist under `/srv/samba/share/podcast-production/work/episodeN/reviews/` or create one from the template; archived state copies remain historical evidence.
2. Use `terminal` from the repository after `source source_me.sh`. Follow the runbook with `stvc.py` and its dedicated setters; use `launchers/set_tags.py` for tags-only changes. Keep commands and editorial conventions owned by their docs.
3. Ground copy and chapters in recording evidence. Treat automatic transcript speaker labels and adjacent greetings as attribution evidence only, not proof of a participant's identity: corroborate cast names against the visible recording, roster references, or a supplied portrait before adding a name to the manifest. Describe desired imagery positively; use the preferred portrait references and compare facial rendering as a separate quality check. When preparing a newly supplied portrait, build a labeled original-photo board, visually inspect that every face and defining hair/identity feature has usable framing, and correct the source crop before public reference hosting or generation. A board filename and manifest do not prove that the reference is fit for likeness work.
4. Before approving a thumbnail, inspect its final 1280x720 export with YouTube's lower-right duration-badge safe area in mind. Move or shorten text that could be obscured; technical image validation alone does not establish publishability. Do not use a watch-page player as proof of listing-tile badge placement, because the player does not render the standard static duration overlay; retain the safe-area review as the decisive check. After upload, fetch the served CDN image with a cache-busting query and compare recognizable composition, headline, cast, and safe area with the accepted export; normal CDN resizing and recompression do not require pixel equality.
5. Carry authorized updates through preparation, agent review, publication, and verification. Routine milestones use agent assessments and existing validators. Dry runs are optional diagnostics. Preserve explicit scope, tool-denial, and private-data-transfer boundaries.
6. If a factual correction changes cast, copy, or other manifest data after an earlier write, update the authoritative episode manifest and rendered copy, publish only the corrected intended fields, and verify against that corrected artifact. Do not call an earlier draft a full match after its source facts changed.
7. Keep production candidates, native masters, original-photo/gameplay references, review copies and upload derivatives in `/srv/samba/share/podcast-production/work/episodeN/`; put operation receipts in `/srv/samba/share/podcast-production/logs/receipts/episodeN/`. Retain episode records in `~/wiki/podcast/episodes/episodeNN.md`; Episodes 1-25 remain in grouped block notes; source transcripts/captions are collected under `~/wiki/podcast/transcripts/`; save selected final art as `~/wiki/podcast/thumbnails/episodeNN.jpg`. Keep `episode.json`, `info.json`, publishing manifests, and pipeline copies in the production workspace. Preserve rejected candidates and their quality findings in production records without presenting them as accepted references. Resume the first unfinished stage after a failure. Reconcile uncertain writes through a fresh `stvc.py fetch` readback and compare every intended field. Normalize the documented YouTube representations before declaring a mismatch: a terminal description newline can be removed and tags can be reordered, so compare description after terminal-newline normalization and tags as an exact set plus count. Do not retry a setter solely for those representations; a fresh readback may already prove the intended state. A setter receipt that reports verification is not the final completion gate if independent readback was not obtained.

## Completion gate

After publication, read back the fields in scope and verify preservation of unrelated meaningful state. For a full episode update, the intended description is nonempty; a thumbnail-only correction preserves the existing description rather than introducing a new content prerequisite. For artwork, compare the current public image with the accepted scene and preferred face style, allowing normal resizing/recompression. When publishing or changing chapters, open the public watch page, expand the description, and open the native chapter panel or "View all" list; confirm every intended chapter title and timestamp there, because description text alone does not prove native chapter navigation. For a thumbnail-only revision, verify preservation of the existing snippet, status and content details through fresh API readback rather than repeating the full description/chapter editorial review; unchanged metadata does not require republication. Reuse adequate fresh evidence across checklist rows; record the exact unresolved surface and continue independent useful work.

Report COMPLETE only when the requested live outcome is verified. A prepared draft, accepted upload, or finished subagent is intermediate progress. Report the video URL, verified changes, and exact remaining work. Repair demonstrated documentation gaps in the canonical docs so the next agent can repeat the workflow.
